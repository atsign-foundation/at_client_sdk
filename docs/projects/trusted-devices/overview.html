Trusted connections — overview

The idea

Tag a connection with the device it comes from. A connection from a device the owner has registered is a trusted connection, and gets authority an ordinary connection does not.

The from: verb already carries a client config — clientId, appName, platform — that the atServer stamps on the connection. Add one field: a device ID.

The hole it closes

A public hidden key (public:_…) is readable today by any unauthenticated connection that knows its name. The _ prefix affects only scan: listings and the access log, so the protection is the name being unguessable — and the read is not recorded. A device-secrecy attribute replaces obscurity with a gate that logs every read.

The rule that makes it safe

A device ID is a name, not a secret — anyone who has seen one can send it. So the device also registers a public key its platform holds (Keychain, TPM, Keystore, authenticator), and a trusted connection signs a fresh server challenge with it. The ID says which device; the signature says this one.

Why the browser cares

Browser storage is evictable, so a web app loses its atKeys on disk pressure or a cleared profile. Recovery is a fresh APKAM enrollment, which today means a human carrying a new OTP, every time.

For the call

  • Does a trusted connection also auto-approve its own re-enrollment? Without it, the OTP goes but the walk to a second device stays; with it, the atServer grants namespaces but cannot re-seal the keys.
  • Refuse synced passkeys? iCloud and Google passkeys always sync; refusing them excludes most Safari and Chrome users.
  • Who reads a device-secrecy key — a device whose keys were evicted, or one registered without enrolling?
  • Who may see the registered devices? Enrollment discovery hands every namespace co-member the record's metadata today.
